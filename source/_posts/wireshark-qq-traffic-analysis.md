本次实验基于 macOS 平台，使用 Wireshark 对手机 QQ 与电脑 QQ 之间的通信过程进行抓包分析，重点研究**传输层协议**、**通信内容的明文特征**以及**文件恢复**的可行性。

## 一、实验过程与成果

1.通过 macOS 的 `lsof` 命令查看 QQ 进程的网络连接信息

```bash
   pgrep -fl QQ
-搜索进程 -f:匹配完整的命令行
         -l:列出进程名字
         
   lsof -nP -iTCP -iUDP
-列出打开的文件
-n:不把 IP 地址反向解析成域名
-P:Port（端口）。不把端口号解析成服务名
-iTCP -iUDP：只显示基于 TCP 和 UDP 的网络连接

   lsof -nP -iTCP -iUDP | grep -i QQ
```

> QQ 进程连接识别：使用 `lsof -nP -iTCP -iUDP | grep -i QQ` 查看进程对应的网络连接。发布时未附原始终端截图，以避免泄露本机环境信息。

学习Wireshark 中的 IP 地址、端口和 TCP 流编号，从而定位 QQ 的 TCP 通信。

- 过滤方式：
    
    #### IP 过滤：从众多通信中挑出与指定 IP 有关的数据。
    
    - 功能一：筛选 IP 地址
        
        例如你想知道：
        
        “我的 Mac 与 `1.1.1.1` 之间发生了哪些通信？”
        
        这时就需要根据 IP 地址过滤数据包。
        
        **所有相关通信：**
        
        ip.addr == 1.1.1.1
        
        只要源 IP 或目的 IP 是 1.1.1.1，就会匹配。
        
        **只看发往目标的数据：**
        
        ip.dst == 1.1.1.1
        
        查看目的 IPv4 地址为 1.1.1.1 的数据包。
        
        **只看目标发来的数据：**
        
        ip.src == 1.1.1.1
        
        查看源 IPv4 地址为 1.1.1.1 的数据包。
        
        这里的 `ip.addr`、`ip.src`、`ip.dst` 是 Wireshark 提供的显示过滤字段。
        
        你要特别区分：
        
        - `src`：Source，源地址。
        - `dst`：Destination，目的地址。
        - `addr`：同时匹配源或目的地址。
    
    #### 协议过滤：只看 TCP、UDP、ARP、DNS 等特定协议。
    
    - 功能二：筛选协议
        
        假设你在同一个接口抓到这些数据：
        
        ```
        ARP
        TCP
        UDP
        DNS
        ICMP
        TCP
        ICMP
        ```
        
        它们并不都在做同一件事情。
        
        例如：
        
        - ARP：在 IPv4 局域网中解析下一跳 IP 对应的链路层地址。
        - ICMP：传递网络控制和诊断信息，比如 ping。
        - TCP：提供**可靠、有序**的字节流传输。
        - UDP：提供**面向数据报**的传输服务。
        - DNS：进行**域名解析**，通常使用 UDP 或 TCP，也可能通过加密传输。
        
        tcp && ip.addr == 1.1.1.1
        同时满足 TCP 与指定 IPv4 地址条件
        
    
    #### 搜索：在捕获内容中查找某个字段、文字或字节序列。
    
    - 功能三：搜索字符串、十六进制和正则表达式
        
        先区分两个操作：
        
        过滤（Filter）：依据某个条件，只显示匹配的数据包。
        
        查找（Find Packet）：在捕获的数据中定位包含某个内容的报文。
        
        例如：
        
        你想查看与 `1.1.1.1` 通信的所有报文，使用过滤。
        
        但如果你想寻找某个报文里是否出现字符串 `Hello`，就**使用查找**。
        
        在 Wireshark 中打开 `Edit → Find Packet`（通常可以使用 `Command + F`），根据界面选择查找类型和范围。
        
        | 查找方式 | 示例 | 用途 |
        | --- | --- | --- |
        | String | `Hello` | 查找指定**文本** |
        | Hex Value | `48 65 6c 6c 6f` | 查找指定**字节序列** |
        | Regular Expression | `Hello[0-9]+` | 匹配具有规律的文本 |
        
        你可能注意到：
        
        `Hello` 为什么对应 `48 65 6c 6c 6f`？
        
        因为字符最终会按照**字符编码**变成字节。以 ASCII/UTF-8 编码中的这些英文字母为例，`H` 对应十六进制 `48`，`e` 对应 `65`。
        
        这里就把你之前学习过的二进制、十六进制和网络数据联系起来了。
        
        但有一个限制：如果应用数据经过 TLS 等加密，Wireshark 通常无法直接在未解密的网络载荷中查到明文 `Hello`。
        
    
    #### TCP 流跟踪：把属于同一条 TCP 连接的内容关联起来分析。
    
    - 功能四：TCP 流跟踪（重点实验）
        
        Mac 本机创建一个简单的 HTTP 通信，不需要 Kali，也不需要访问其他设备。
        
        ## 第一步：在 Mac 终端启动本地 Web 服务
        
        打开第一个终端窗口：
        
        ```
        python3 -m http.server 8000 --bind 127.0.0.1
        ```
        
        如果 Python 已安装并正常运行，终端会显示服务已启动的信息。
        
        这表示你在 Mac 上启动了一个仅监听本机回环地址 `127.0.0.1`、端口为 `8000` 的 HTTP 服务。
        
        保留这个终端窗口。
        
        ## 第二步：在 Wireshark 中捕获本机通信
        
        打开 Wireshark，选择 `lo0` 回环接口，开始抓包。
        
        这次为什么不用 `en0`？
        
        因为我们要观察的是 Mac 自己访问自己的通信，不经过外部 Wi-Fi 网卡。
        
        随后打开第二个终端窗口，执行：
        
        ```
        curl --http1.1 -v http://127.0.0.1:8000/
        ```
        
        这会向刚才启动的本地 HTTP 服务发送请求。
        
        返回内容可能包含目录列表、HTTP 响应头等信息，具体取决于运行服务时的目录。
        
        ## 第三步：在 Wireshark 中过滤 TCP
        
        输入显示过滤器：
        
        ```
        tcp.port == 8000
        ```
        
        你应该能观察到对应端口的 TCP 报文。
        
        这些报文可能包括：
        
        ```
        SYN
        SYN, ACK
        ACK
        HTTP GET
        HTTP Response
        FIN, ACK
        ```
        
        实际报文数量和拆分方式可能不同。
        
        ## 第四步：跟踪 TCP 流
        
        选中相关 TCP 报文，右键选择：
        
        Follow → TCP Stream
        
        Wireshark 会把属于同一条 TCP 流的两个方向的数据组织到一个窗口中。
        
        你可能看到类似：
        
        ```
        GET / HTTP/1.1
        Host: 127.0.0.1:8000
        User-Agent: curl/...
        ```
        
        以及服务端返回的 HTTP 响应。
        
        这里你应该建立一个很重要的认识：
        
        TCP 负责传输字节流，HTTP 是利用这条 TCP 连接交换应用层请求和响应的协议。
        
        TCP 流跟踪能帮助你从多条分散的 TCP 报文中，理解应用两端交换了哪些字节；它不代表网络中原本就存在一条完整、未分段的“HTTP 大报文”。
        
        实验结束后，在第一个终端按 Control + C 停止本地 HTTP 服务。
        

然后重新启动 QQ 并且进行抓包，成功捕获 TCP 三次握手，进一步结合 Seq、Ack、Len 字段理解 TCP 的字节编号和确认机制

## 二、实验中遇到的问题

本次实验经历了多次排查，在过滤中，使用：

1：

```bash
去噪与精准定位：tcp.len > 0
锁定单一会话：tcp.stream == N
观察连接状态：tcp.flags.ack == 1或0
锁定特定端口号：tcp.port ==
在 TCP 的载荷（Payload，即数据体）中搜索十六进制特征码：tcp.payload contains ff:d8:ff
tcp.ack ==
、、、、等等的条件
```

**2：`统计 (Statistics) -> 会话 (Conversations)`**

点开 TCP 或 UDP 标签页，按“数据包 (Packets)”或“字节 (Bytes)”排序。较大的流量可以作为候选，但不能仅凭大小就认定属于 QQ，仍需结合进程、地址与时间验证。

最初因抓包时间较晚，未能观察到部分连接的建立过程；随后又因缺少进程信息，难以准确区分 QQ 流量和其他应用流量。

经过分析，最终采用 Wireshark 的 Raw 导出功能，并借助 010 Editor 直接操作二进制字节，解决了文件恢复问题。

## 三、实验结论与回答

实验确认 QQ 客户端可以存在 TCP 的通信方式，并发现一条与 QQ 相关的 HTTP **明文**图片传输连接，能够从捕获的数据中恢复 JPEG 图片。

但不能据此推断 QQ 的全部通信均为明文，也尚未确认聊天消息的具体加密方式及 UDP 在本次消息传输中的作用。

同时发现：用 `lsof` 查找 QQ 进程时，会看到很多 `127.0.0.1`，但 Wireshark 抓到的 QQ 通信却是其他 IP 地址。

```
127.0.0.1:xxxxxx1 → 127.0.0.1:xxx2
```

这说明 QQ 相关组件在电脑内部进行通信。

另一条：

```
[Mac IPv6]:60711 → [服务器 IPv6]:14000
```

则是 QQ 与外部服务器建立的 TCP 连接。

结论：QQ 可以同时存在内部通信和外部网络通信。
